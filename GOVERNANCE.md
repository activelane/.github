# ActiveLane Governance

## Current model

ActiveLane is currently a founder-led, early-stage project maintained primarily by one developer.

The project is not yet governed as a foundation, standards body, or multi-maintainer consortium. The lead maintainer is responsible for product direction, architecture, releases, repository permissions, security decisions, moderation, and final merge decisions.

This model is intended to be explicit rather than permanent.

## Decision principles

Material decisions should be evaluated against the following questions:

1. Does this make it easier to create useful software, find users, earn from it, or build lasting value?
2. Does it preserve the distinction between Product, Release, Distribution, Extension, Publisher, Owner, Entitlement, Library, and Installation?
3. Does it maintain capability-driven Web and Desktop hosts?
4. Does it preserve first-class offline and air-gapped operation?
5. Does it improve or weaken security, privacy, and user control?
6. Can the current maintainers operate and support it sustainably?
7. Is it justified by evidence from the active milestone?

## Types of decisions

### Routine implementation

Small fixes and internal changes may proceed through normal issue and pull-request review.

### Significant changes

Public APIs, package formats, persisted schemas, security boundaries, major dependencies, repository boundaries, and product-level changes should begin with a written proposal.

A proposal should cover:

- the problem and affected users;
- constraints and alternatives;
- compatibility and migration;
- security and privacy impact;
- operational cost;
- and how success will be verified.

### Architecture decisions

Accepted architectural decisions should be recorded in the relevant repository as Architecture Decision Records. Decisions may be superseded, but their history should remain available.

## Maintainers

Maintainer access is granted based on sustained, trustworthy contributions and demonstrated judgment—not contribution count alone.

Repository roles may eventually distinguish:

- triage;
- documentation;
- component maintenance;
- release management;
- security response;
- and organisation administration.

Least privilege should be used, especially for releases, registries, signing, infrastructure, and security information.

## Roadmap

The roadmap communicates direction rather than a promise of dates or inclusion. The active milestone takes precedence over speculative later phases.

Complex work requiring legal, tax, security, compliance, enterprise operations, moderation, or round-the-clock support will be postponed until the project can obtain appropriate professional and organisational capacity.

## Conflicts of interest

Maintainers and contributors should disclose material interests that could reasonably affect decisions involving marketplace ranking, verification, product moderation, commercial terms, acquisitions, or competing products.

## Future evolution

Governance should evolve when there are multiple sustained maintainers, meaningful creator and user communities, commercial responsibilities, or stewardship questions that should not depend on one person.

Possible future changes include component ownership, public proposal processes, independent security review, creator advisory groups, and formal company or foundation governance. None should be claimed before it exists in practice.
